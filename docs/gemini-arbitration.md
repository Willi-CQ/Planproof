# Gemini review of disputed door detections

The first V3 workflow compares door assemblies on one selected drawing page. Both engines work on the same raster. Python compares the door regions one by one. If the engines report a localized discrepancy, Gemini can inspect the original crop and return an advisory with evidence IDs. The API keeps the result at `NEEDS_REVIEW` after an advisory. A model opinion alone cannot establish the exact count or full-page coverage.

## Run the demo

From the repo root in the same Python environment used for the backend:

```powershell
python -m pip install -r backend/requirements.txt
python -m uvicorn app:app --app-dir backend --reload
```

Open [Planwise](http://127.0.0.1:8000/planwise/) and click **Tester le plan d’exemple**. For separate scenarios, use **POST /api/v1/demo/door-count** in [the API test page](http://127.0.0.1:8000/docs).

| Scenario | Expected response |
| --- | --- |
| `agreement` | `SUPPORTED`, count 2, with matched boxes |
| `disputed` | `NEEDS_REVIEW`, with one disputed box |
| `missing_ml` | `INSUFFICIENT_EVIDENCE`, with ML marked unavailable |

These responses are labeled `synthetic_demo`. Both test detections are generated by the demo. The `image_url` opens its source page.

## Enable real Gemini review

Sign in to [Google AI Studio](https://aistudio.google.com/api-keys) with the event account and copy the API key from the assigned project. Use **Import project** if it is missing. Follow [Google's event account guide](https://goo.gle/hackathon-account).

From the repo root, run this command in PowerShell:

```powershell
python backend/check_gemini.py --serve
```

Paste the API key when prompted, then press Enter. The input is hidden and the key stays in the running process. The script sends one synthetic crop with `gemini-3.8-flash` by default. On success it opens the API on port 8001. Try **POST /api/v1/demo/door-count** with `scenario=disputed` and `allow_gemini_review=true` at [localhost:8001/docs](http://127.0.0.1:8001/docs). Omit `--serve` to run only the check. Set `GEMINI_MODEL` in PowerShell to use another available model.

For a regular uvicorn launch, set `GEMINI_API_KEY`, `GEMINI_MODEL` and `GEMINI_ENABLED=true` in the server environment. For uploaded drawings, enable review only when the source can be sent to Gemini.

The backend submits one original PNG crop, the two counts, the reason for review and the disputed candidate IDs. It skips review for more than eight disputed candidates or a crop covering more than half the page. The response includes an advisory, cited IDs and the bounds of the crop where available. Gemini failures preserve the local result and its evidence.

## Connect the engines

The Planwise upload flow uses **POST /api/v1/documents/{document_id}/analyze-doors** to launch configured engines. Both runners receive the PNG served by the viewer. Use separate Python environments if their requirements differ. Install the deterministic package from branch `iamd-johan-deterministic-fix`, or from `norlan-deterministic` once it includes the OpenCV shape fix. Install Willi's `ml` package and its dependencies in Python 3.11 or 3.12, then fetch the selected model and calibration from Git LFS. [Deterministic source and fix](https://github.com/Willi-CQ/Planproof/tree/iamd-johan-deterministic-fix) · [ML release](https://github.com/Willi-CQ/Planproof/tree/ml/trained-baseline-v1/models/baselines/v1)

```powershell
$env:PLANPROOF_DETERMINISTIC_PYTHON = 'C:/path/to/deterministic-venv/Scripts/python.exe'
$env:PLANPROOF_ML_PYTHON = 'C:/path/to/ml-venv/Scripts/python.exe'
$env:PLANPROOF_ML_CHECKPOINT = 'C:/path/to/corrected-3500-global/detector.pt'
$env:PLANPROOF_ML_CALIBRATION = 'C:/path/to/corrected-3500-global/calibration.json'
python backend/check_gemini.py --serve
```

Open [Planwise with Gemini enabled](http://127.0.0.1:8001/planwise/). To run without Gemini, use the regular uvicorn command above. Missing engines are reported as unavailable. The service runs analyses one at a time and each engine has a 120-second deadline.

### Submit results from separate engine runs

1. Upload a PDF, PNG or JPEG using **POST /api/documents** and select the page for a PDF. Save its `image_url` as `page.png`.
2. Fetch **GET /api/v1/documents/{document_id}/frame**. The frame identifies the original file and the exact decoded RGB image. Page indexes start at zero. Boxes use pixel edges from the top left, ordered `[x0, y0, x1, y1]`.
3. Run Willi's documented `planproof-ml infer` command on that PNG, with the same `--page-index` and **without `--document-id`**. This makes the release record the input RGB hash.
4. Post an object with the upload's `document_id`, the original `detections.json` object under `ml_detections`, and the normalized result of the independent engine under `deterministic` to **POST /api/v1/door-count**. Set `allow_gemini_review` only for an authorized drawing. The fields are described under `AnalyzerResult` in the API docs. The deterministic adapter records the frame it processed, its version and mode, and door IDs and boxes in the same coordinates. Use `mode: "hybrid"` when the result depends on the other engine.

The API also accepts a normalized ML result under `ml` in place of `ml_detections`. The CLI `python backend/ml_adapter.py detections.json frame.json` remains available for inspecting that normalized result. Provide outputs from trusted local engine runners. The API checks the reported frame against its registered page. The ML adapter checks the release's recorded raster hash and leaves coverage unknown. With one engine unavailable, its counterpart's boxes appear in `unverified_evidence` and the answer is null. A count is supported only when both independent results report complete coverage and match one-to-one without ambiguous duplicates. The initial box overlap threshold is IoU 0.5. Tune it on real annotated drawings before relying on it.

For an ML-only smoke test, start the backend and prepare the canonical raster:

```powershell
$api = 'http://127.0.0.1:8000'
$doc = curl.exe --silent --show-error --fail -F 'file=@plan.pdf' -F 'page=1' "$api/api/documents" | ConvertFrom-Json
$frame = Invoke-RestMethod "$api/api/v1/documents/$($doc.document_id)/frame"
Invoke-WebRequest "$api$($doc.image_url)" -OutFile page.png
```

In Willi's Python 3.11/3.12 ML environment, from the clone of his baseline branch, run the verified main bundle on that raster. Use absolute paths for the input and output when the two clones live in different directories.

```powershell
$bundle = 'models/baselines/v1/corrected-3500-global'
planproof-ml infer --checkpoint "$bundle/detector.pt" --calibration "$bundle/calibration.json" --global-view --image 'C:/path/to/page.png' --page-index 0 --out 'C:/path/to/ml-output' --device cpu
```

Return to the PowerShell session that holds `$doc`. Post the detections as JSON:

```powershell
$body = @{
    document_id = $doc.document_id
    ml_detections = (Get-Content -Raw 'C:/path/to/ml-output/detections.json' | ConvertFrom-Json)
} | ConvertTo-Json -Depth 30
Invoke-RestMethod "$api/api/v1/door-count" -Method Post -ContentType 'application/json' -Body $body
```

An ML-only result should show `INSUFFICIENT_EVIDENCE`, the observed candidate count in `ml.detected_count`, and any candidate boxes in `unverified_evidence`. A zero candidate count alone does not establish that no door is present.

## Verify locally

```powershell
python -m unittest discover -s backend -v
```

This runs against synthetic detections and mocks the Gemini transport. The trained detector and deterministic engine can be verified independently on the same canonical PNG before connecting their outputs.
